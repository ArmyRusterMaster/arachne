# 8. План разработки и dev-опыт

> **Принцип приоритизации:** сначала — **максимально общий вариант**: Fast HTTP-ядро «штампа» (Фаза A), затем полноценный single-node с собственным движком (Фаза B), затем мультинода (Фаза C). Интеграции с тяжёлыми/специфичными зависимостями (LLM, eBPF, распределённые ноды, резидентные прокси/DNS) — **отложены на поздние этапы** и не блокируют базовый функционал. SaaS-платформа — **вне фаз** (перспектива, [19-saas-platform.md](19-saas-platform.md)).

## 8.1. Чек-лист старта разработки

Старт разработки = **Фаза A («Штамп-ядро»)**, вехи M0–M4 — в разделе 8.2. Ключевое:

- **Первым делом — спайк M0:** простой бинарник с `rquest`. Отправить запрос на защищённый сайт (`https://nowsecure.nl` или любой сайт под Cloudflare). Добиться успешного ответа без бана. Если BoringSSL не собирается на Windows — dev-таргет переносится в WSL/Linux ([14-linux-target.md](14-linux-target.md)).
- **Движок и Smart Router в Фазу A не входят** — это Фаза B. Ядро-«штамп» закрывает статический HTML/API: парсинг, пагинация, ротация прокси, экспорт.
- Декларативный `job.yaml` вместо жёстко закодированных сценариев — веха M3.

### Инвариант разработки: тесты идут попутно, профиль — после крупных фаз

- **Попутное написание тестов (TDD-инвариант).** Писать **тесты сразу вместе с кодом**: новый тип/функцию/фичу — в одном коммите с их тестами. Отдельного «этапа тестирования» нет — тест пишется той же правкой, что и код.
- **Минорные изменения → минорные тесты**: багфикс/опция/рефакторинг — минимум 1 тест на изменённое поведение и на граничный случай.
- **После каждой КРУПНОЙ логической фазы** (новый модуль, смена архитектуры, завершение крупного этапа ниже) — **обязательно профилирование и оптимизация**:
  1. `cargo flamegraph` / `perf` — найти узкие места (CPU, аллокации, блокировки, memcopy).
  2. Бенчмарки `criterion` для hot-path (парсер, транспорт, стриминг) — зафиксировать **baseline**.
  3. Оптимизировать найденное, обновить/добавить тесты, повторно прогнать профиль — метрики не регрессируют.
  4. Краткий **отчёт о профилировании** — в профили-разделе ниже.

## 8.2. Дорожная карта: фазы A → B → C (SaaS — вне фаз)

Три фазы, каждая — **самодостаточная точка выхода**: если проект остановится после любой фазы, остаётся рабочий продукт. Переход к следующей фазе — **по спросу, не по календарю**.

| Фаза | Что входит | Этапы (детализация ниже) | Гейт готовности | Точка выхода, если остановиться |
|---|---|---|---|---|
| **A. Штамп-ядро** | workspace + CQRS-каркас, `rquest` (TLS-имперсонация, cookies, ротация прокси, rate-limit + гауссов джиттер), очередь URL + дедуп + resume, парсер (`scraper`/`html5ever`), экспорт CSV/JSONL/SQLite, CLI + `job.yaml` (включая вложенные CSS-селекторы для извлечения структурированных списков), CI, Linux-таргет | 0, 1, часть 4 | Устойчивый прогон 10к–100к страниц без бана, resume после kill -9, профиль-отчёт | Рабочий фриланс-инструмент «штамп» для типовых задач (спарсить 10к страниц и т.п.) |
| **B. Полноценный single-node** | Собственный движок (`boa_engine` + DOM, нативные биндинги, JS-полифилы), Smart Router с эскалацией, cookie-мост, OOM token bucket, zero-copy DOM-стриминг, пул прогретых сессий, Shadow Recorder + REPL; опционально за флагами: продвинутые прокси ([15-proxy-infra.md](15-proxy-infra.md)), LLM ([16-llm.md](16-llm.md)) | 2, 3, остаток 4, 5 | Стабильное прохождение JS-защит (Cloudflare-класс), чек-листы 02/03/04 зелёные | Полноценный Arachne как CLI/библиотека, кейсы посложнее |
| **C. Мультинода + платформы** | Master/Worker поверх готовой CQRS-шины ([18-distributed.md](18-distributed.md)), платформенная матрица: musl/контейнеры/systemd/ARM64 ([14-linux-target.md](14-linux-target.md)), распределённая observability ([07-observability.md](07-observability.md)); eBPF ([17-ebpf.md](17-ebpf.md)) — опционально, Linux-only | 6 п.4 + углубление 14 | N воркеров масштабируют throughput линейно; отказ воркера не рвёт задачу | Масштабируемый комбайн для больших объёмов |

**SaaS-платформа — вне фаз:** остаётся перспективной заметкой в [19-saas-platform.md](19-saas-platform.md) **без гейтов**; решение о старте принимается отдельно от инженерной дорожной карты (SaaS не требует кластера — может работать поверх single-node).

### Гейты переходов (по спросу)

- **A → B:** фриланс-задачи упёрлись в JS-защиты, которые Fast HTTP не проходит — тогда движок окупается. Пока статика/API проходит `rquest`-ом — в Фазу B не лезем.
- **B → C:** одна нода насыщается (CPU/сеть/лимиты домена) или появляются объёмы, которые одной нодой не прожать.

### Фаза A — вехи M0–M4

> **Статус Фазы A:** workspace создан (6 крейтов, см. [README](README.md#статус)), M0 закрыт частично (см. решение ниже), M1 реализован. **Решение по спайку M0:** крейт `rquest` отзнан (yanked) автором с crates.io; преемник — **`wreq`** (тот же автор, форк reqwest). BoringSSL (`wreq`) требует clang/LLVM — на текущей dev-машине Windows clang отсутствует, поэтому: (а) базовый dev-путь — pure-Rust `reqwest`+`rustls` (собирается без C-тулчейна), (б) полная TLS-имперсонация — за фича-флагом `impersonation` (feature `arachne-net/impersonation`), включается на Linux/WSL-таргете или после установки clang. Это соответствует фоллбэку «dev через WSL/Linux» из этого раздела.

- **M0 — Спайк транспорта (риск-первый):** workspace + компиляция `rquest`→**`wreq`** (BoringSSL) на Windows; запрос к защищённому сайту без бана. Фоллбэк: dev через WSL/Linux-musl. **[ЧАСТИЧНО: fallback-бэкенд работает; имперсонация за флагом]**
- **M1 — Одна страница → запись:** fetch → DOM → CSS-селекторы → типизированная запись → JSONL. Тесты попутно (фикстуры HTML в `tests/fixtures`). **[РЕАЛИЗОВАН: крейты domain/net/parse/export + CLI]**
- **M2 — 10к страниц:** пагинация (next-селектор / URL-шаблон / sitemap), per-domain concurrency, rate-limit с гауссовым джиттером, retry+backoff, дедуп URL, чекпоинт очереди на диск (kill -9 → resume). **[ЧАСТИЧНО: retry+backoff и джиттер есть; очередь/дедуп/чекпоинт — впереди]**
- **M3 — «Штамп»:** декларативный `job.yaml` (start_urls, пагинация, селекторы, лимиты, экспорт, прокси) → `arachne crawl job.yaml -o out.csv`. Готовый шаблон под типовой заказ. **[ЧАСТИЧНО: job.yaml читается (start_urls, селекторы, прокси, limit, экспорт по расширению); пагинация — впереди]**
- **M4 — Профилирование и оптимизация:** flamegraph + criterion baseline на hot-path (`arachne-net`, `arachne-parse`), отчёт в `docs/benches/` (см. 8.3). **[НЕ НАЧАТ]**

**Скоуп-дисциплина Фазы A:** НЕ входить — собственный JS-движок (`boa_engine`), Smart Router-эскалация, LLM, eBPF, кластер, SaaS. `scraper`/`html5ever` — это чистый DOM-парсер, не браузер: их использование в Фазе A не нарушает отказ от готовых браузеров ([11-browser-engines.md](11-browser-engines.md)).

### Детализация по этапам

Этапы ниже — детализация внутри фаз: **Фаза A** = этапы 0, 1 и часть 4 (CLI/экспорт); **Фаза B** = этапы 2, 3, остаток 4, 5; **Фаза C** = этап 6 п.4 и платформенная матрица 14.

### Этап 0. Фундамент (первый приоритет)
- Рабочий `Cargo.toml` с базовыми зависимостями: `tokio`, `rquest`, `serde`, `cookie_store`, `tracing`, `bytes`, `thiserror`, а также **lock-free** `flume`/`crossbeam-channel`, `dashmap`.
- Модульная структура проекта (`domain`-типы с Newtype, ошибки через `thiserror`, конфиг через `serde`).
- **CQRS-каркас с первого дня**: трейт `Bus` (команды `Command`/запросы `Query`), раздельные пути — чтобы позже перейти в мультинодный режим без переписывания (см. [05-rust-patterns.md](05-rust-patterns.md#58-cqrs-принцип-команды-и-запросы-для-стриминга-и-мультинодности)).
- CI-сборка и линтеры (см. [13-cicd-docker.md](13-cicd-docker.md)).
- Заготовка под Linux-таргет (см. [14-linux-target.md](14-linux-target.md)) — сразу, чтобы не переписывать платформенно-зависимый код.
- **Попутные тесты (этап 0):** каждый пункт этапа сопровождается юнит/интеграционными тестами (TDD-инвариант); этап закрыт только при зелёных `cargo test`.

### Этап 1. Стелс-транспорт и архитектура сессий (базовый)
- Структура `StealthSession`: HTTP-транспорт + менеджер cookie.
- Настройка `rquest`: авто-генерация TLS-отпечатков последних версий Chrome/Firefox, синхронизация с HTTP/2-заголовками.
- Модуль прокси: динамическая смена прокси-серверов с авторизацией для каждого сетевого потока (базовая ротация — [06-infrastructure.md](06-infrastructure.md)).
- **Попутные тесты (этап 1):** тесты на генерацию TLS-отпечатков, cookie-мост, ротацию прокси — в том же коммите.

### Этап 2. Собственный модульный движок и маскировка JS (базовый)
- Сборка движка из своих крейтов: `boa_engine` (JS) + `html5ever`/`scraper` (DOM) — **без готовых браузеров** ([11-browser-engines.md](11-browser-engines.md)).
- JS-заглушки (Mocks): инициализационные скрипты до скриптов целевого сайта, подмена `navigator.plugins`, WebGL-отпечатков.
- Синхронизатор контекста: экспорт/импорт cookie между сетевым клиентом и хранилищем движка.
- **Попутные тесты (этап 2):** фикстуры DOM-парсинга, скриншот-тесты моков JS, тесты синхронизации cookie.

### Этап 3. Smart Router и движок макросов (базовый)
- Автовыбор режима Fast/Headless: эвристики + эскалация по ответу ([03-smart-routing.md](03-smart-routing.md)).
- Схема сценария (JSON/YAML): `Click`, `Type`, `Wait`, `Scroll`, `Hover` — транслируются в **команды** CQRS-шины (`Command`), а данные возвращаются **запросами** ([05-rust-patterns.md](05-rust-patterns.md#58-cqrs-принцип-команды-и-запросы-для-стриминга-и-мультинодности)).
- Интерпретатор макросов: трансляция шагов в JS-события DOM (`dispatchEvent`, `MouseEvent`).
- Рандомизатор поведения: «человеческие» задержки, движение курсора по кривым Безье.
- **Попутные тесты (этап 3):** тесты трансляции сценария в команды CQRS, интерпретатора макросов, рандомизатора (детерминированный RNG).

### Этап 4. Тестирование, оптимизация, API (базовый)
- Антибот-тесты: CreepJS, Pixelscan, Cloudflare Challenge — выявление и устранение утечек фингерпринтов.
- Менеджмент памяти: жизненный цикл JS-контекстов, Token Bucket на RAM ([04-architecture.md](04-architecture.md)).
- API/CLI для запуска со списком прокси и файлом сценария.
- **Попутные тесты (этап 4):** интеграционные тесты «сессия->cookie->движок->ротация» через mock-сервер; антибот-скриншоты как e2e-тесты с детерминированным RNG.

### 8.3. Профилирование и отчёт (после каждой крупной фазы)

После завершения крупной фазы (этапы 0–4, а далее каждый крупный модуль/интеграция из этапа 6) — **профилирование и оптимизация**:

1. **Профилировщик:** `cargo flamegraph` / `perf` (горячие пути: парсер `arachne-dom`, транспорт-обвязка `rquest`, lock-free конвейер `arachne-stream`) — найти аллокации, блокировки, memcopy.
2. **Бенчмарки:** `criterion` на hot-path, фиксируем **baseline** (в `benches/`), target-норма — не регрессия относительно прошлого замерка.
3. **Оптимизация:** устраняем найденные узкие места, добавляем/обновляем тесты, повторяем профиль. Результат — «профили-отчёт»: что мерили, что нашли, что сделали, насколько (время/память).
4. Отчёт сохраняется в `docs/` возле этапа (напр. `docs/benches/`), хранит метрики baseline для будущих сравнений.

> Профили-отчёт обязателен к мержу крупной фазы — без него PR не принимается (см. [13-cicd-docker.md](13-cicd-docker.md)).

### Этап 5. Dev-опыт
- «Теневая запись» (Shadow Recorder): расширение для Chrome/Firefox, транслирующее действия человека в YAML/JSON-макрос.
- REPL-отладчик: пауза макроса, выполнение JS/CSS в живой вкладке движка ([07-observability.md](07-observability.md)).

### Этап 6. Поздние интеграции (реализуются в САМЫЙ последний момент)
Порядок внутри этапа — от более ценного к более экспериментальному:
1. **Proxy-инфраструктура продвинутая**: резидентные/мобильные прокси, IP Reputation, локальный DNS-резолвер с DoH — [15-proxy-infra.md](15-proxy-infra.md).
2. **LLM-интеграции**: LLM-Vision селекторы, локальное решение капч (ONNX) — [16-llm.md](16-llm.md).
3. **eBPF / TUN-TAP**: модификация TCP-стека на уровне ядра Linux — [17-ebpf.md](17-ebpf.md).
4. **Распределённые ноды**: Master/Worker кластер — [18-distributed.md](18-distributed.md). Подключается по уже готовой CQRS-шине и lock-free конвейеру — менять ядро не нужно, только добавить транспорт очереди.
5. **SaaS-платформа — вне фаз** (перспектива без гейтов; решение о старте отдельно): low-code конструктор из блоков, мультитенантность, биллинг (подписка/оплата за запрос), резидентные прокси как сервис, публичный API по ключам; веб-слой `axum` + `leptos` (SSR/CSR) — [19-saas-platform.md](19-saas-platform.md).

> Идея: базовый вариант обязан работать **без** любого из этих компонентов — каждая поздняя интеграция подключается за фича-флагом (feature flag) и не ломает общий вариант.

## 8.5. Веб-интерфейс на Rust

Перспективное направление: **веб-UI на Rust и Leptos** (помимо CLI) для управления комбайном и просмотра observability-данных. Реализуется после стабилизации базового ядра.

Полноценное развитие (SaaS: low-code конструктор сценариев из блоков, мультитенантность, биллинг по подписке/запросу, резидентные прокси как сервис, публичный API по ключам; стек `axum` + `leptos` с гибридом SSR+CSR) — подробно описано в [19-saas-platform.md](19-saas-platform.md) и находится **вне фаз** (перспектива; SaaS может работать поверх single-node — кластер ему не требуется).

## 8.6. Чек-лист сессии разработки

- [ ] Все типы — Newtype где нужно ([rules.md](../rules.md)).
- [ ] Состояния — Typestate, невалидные переходы невозможны по типам.
- [ ] Ошибки — через `thiserror` в библиотечных крейтах, `anyhow` только в бинарнике.
- [ ] Нет `unwrap()`/`expect()` вне тестов.
- [ ] Взаимодействие между потоками — команды/запросы через CQRS-шину, без прямых вызовов между модулями ([05-rust-patterns.md](05-rust-patterns.md#58-cqrs-принцип-команды-и-запросы-для-стриминга-и-мультинодности)).
- [ ] Горячие пути — lock-free (`flume`, `DashMap`, атомики), без `Mutex<HashMap>`.
- [ ] Не внедряем готовый браузер — движок из своих крейтов ([11-browser-engines.md](11-browser-engines.md)).
- [ ] Платформозависимый код — за `#[cfg(...)]`, оба таргета (Windows/Linux) собираются в CI.
- [ ] Каждая правка кода сопровождена **попутным тестом** (TDD-инвариант): нет кода без теста в том же коммите.
- [ ] Минорное изменение → минорный тест (поведение + граничный случай).
- [ ] Крупная фаза → выполнено **профилирование и оптимизация** (flamegraph/perf + criterion baseline), профиль-отчёт в `docs/`.
- [ ] `cargo test --workspace` зелёный; для e2e-сценариев — с `--features e2e` и mock-сервером/`--ignored`.
