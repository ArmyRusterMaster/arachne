# 7. Мониторинг, отладка и логирование (Observability)

## 7.1. Трассировка через `tracing` вместо `log`

Веб-скрейпинг — это хаос (сетевые таймауты, изменения версий сайтов, капчи). Обычные логи не помогают понять, на каком именно шаге макроса упал конкретный поток из тысячи параллельных.

**Решение:** крейт `tracing`, позволяющий создавать контекстные **«спаны» (spans)**. К каждому логу привязываются:
- ID сессии;
- целевой URL;
- текущий шаг макроса.

Если поток падает, видна полная цепочка событий, приведшая к бану.

## 7.2. Сохранение слепков состояния (State Dumps)

При возникновении ошибки (`ElementNotFound`, `CaptchaTriggered` и т.п.) собственный движок автоматически дампит три вещи:
1. **Текущий снимок виртуального DOM-дерева** в формате `.html`;
2. **Содержимое Cookie Jar и localStorage** в JSON-файл;
3. **Полный лог выполненных JS-инструкций**.

Это позволяет мгновенно воссоздать упавшую сессию на локальной машине для отладки.

## 7.3. Интерактивная консоль отладки (REPL Debugger)

Возможность поставить макрос на паузу в терминале Rust и в реальном времени выполнять JS-команды или CSS-селекторы внутри запущенной вкладки движка (JS-контекст `boa_engine`), чтобы понять, почему скрипт упал на конкретном шаге.

## 7.4. Рекомендации

- Продумать observability на ранних этапах (не после релиза).
- Связать свои «спаны» с событиями стелс-движка для полной картины каждой сессии.
