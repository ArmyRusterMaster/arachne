# 18. Распределённые ноды / кластеринг (отложенный этап)

> Распределённый режим — **один из последних этапов** ([08-development.md](08-development.md), этап 6.4). Базовый вариант — **одиночный бинарник**, который работает без всякого кластера. Кластер — это способ масштабировать уже работающее ядро, а не наоборот.

## 18.1. Идея (Cluster Mode)

Запуск **одного и того же бинарника** в двух ролях:
- **Master** — управляет очередью команд, раздаёт макросы и прокси, собирает результаты;
- **Worker** — лёгковесный агент, который только крутит собственный движок и `rquest`.

Позволяет развернуть краулер на сотнях дешёвых VPS и собирать данные терабайтами, масштабируя горизонтально.

## 18.2. Ключевые принципы (чтобы не убить одиночный режим)

1. **Монолит прежде всего**: единый бинарник умеет роль Master и Worker, выбирая её конфигом/CLI (`--role master|worker`).
2. **Worker — тонкий**: не тащит в себя LLM/маршрутизацию сценариев в полном объёме, только «крутит голову» сеть и сессии.
3. **Коммуникация через очередь**: команды — JSON-пакеты через Redis/SQS/NATS; результат — тот же формат. Ни какого custom TCP-протокола на первый релиз.
4. **Идемпотентность задач**: повторная доставка одной команды не даёт дублей в результирующем наборе (ключ по `task_id`, см. Newtype в [05-rust-patterns.md](05-rust-patterns.md#52-паттерн-newtype)).
5. **Feature-flag**: весь кластер — за `--features cluster`, не в базовом бинарнике.
6. **CQRS-дизайн с самого начала** (даже в одиночном бинарнике): команды и запросы разделены (см. 18.3).

## 18.3. CQRS, команды и стриминг (закладывается с самого начала)

> Ключевая идея: **даже одиночный бинарник проектируется как CQRS-система** — команды и запросы разделены, всё максимально стримингово и асинхронно. Это делает переход в мультинодный режим почти бесплатным: **локальное межпоточное сообщение == распределённое сообщение по очереди**.

**Команды** (`Command`) — изменяют состояние (эскалация, ротация прокси, запуск задачи). **Запросы** (`Query`) — читают данные (статус, результаты), без побочных эффектов. Шина команд/запросов реализуется единым трейтом `Bus` (пример — [05-rust-patterns.md](05-rust-patterns.md#58-cqrs-принцип-команды-и-запросы-для-стриминга-и-мультинодности)):

- единый бинарник уже передаёт команды/запросы по lock-free каналам внутри себя (локальная шина);
- когда включается `--features cluster`, та же `Command`/`Query` идёт через Redis/NATS (распределённая шина) — менять вызывающий код не нужно;
- стриминг: результаты текут кусками через `futures::Stream`/каналы с backpressure, а не ждут полной готовности;
- асинхронность: каждый узел конвейера — отдельная task (`tokio`), всё параллельно, без блокировок.

## 18.4. Lock-free структуры данных

Мультинодный режим строится на тех же lock-free структурах, что и одиночный (см. [05-rust-patterns.md](05-rust-patterns.md#57-локфри-структуры-данных-и-асинхронная-конвейерная-обработка)):
- очереди задач — `flume`/`crossbeam-channel` (MPMC, no-block);
- реестр воркеров/сессий — `DashMap` (конкурентная карта без блокировок на чтение);
- счётчики прогресса — `AtomicU64`/`AtomicUsize`;
- никаких `Mutex<HashMap>` в горячих путях — это резко снижает конкурентную деградацию при масштабировании на сотни воркеров.

## 18.5. Схема развёртывания

```
                    ┌──────────────┐
                    │   Master     │  очередь команд, публикация в Redis
                    │ (араchnе)    │  сбор результатов
                    └──────┬───────┘
                           │  Redis / NATS (команды + запросы)
        ┌──────────────────┼──────────────────┐
        │                  │                  │
   ┌────▼────┐        ┌────▼────┐        ┌────▼────┐
   │ Worker1 │        │ Worker2 │        │ WorkerN │
   └─────────┘        └─────────┘        └─────────┘
   прокси: Р1,Р2        прокси: Р3,Р4       прокси: Р5...
```

## 18.6. Прототип (первый релиз, минимум)

- Реестр воркеров: heartbeat в Redis (`HSET workers:{id}` + TTL);
- очередь команд: `LPUSH/BLPOP` в Redis;
- health-check: воркер с N-провальных команд подряд признаётся «сгоревшим» master'ом;
- результат: стримится кусками через файловый sink / HTTP-пуш.

## 18.7. Ограничения и риски

- Требует инфраструктуру (Redis/очередь) — это отдельный деплой;
- общих крипто-сессий между воркерами нет; у каждого своя сессия/пул прогрева;
- отказоустойчивость: если Master падает, очередь не теряется (Redis AOF), а задачи идемпотентны.

## 18.8. Чек-лист (флаг `cluster`)

- [ ] Реализация под `--features cluster`; без флага бинарник — одиночный и лишних фич не тащит.
- [ ] Очередь команд — через feature (Redis/NATS/SQS), вызов через трейт `Bus` (CQRS-шина).
- [ ] Команды/запросы локальной шины == распределённой шины (без отдельного API под кластер).
- [ ] Результаты стримятся (каналы + backpressure), а не накапливаются целиком.
- [ ] Горячие пути на lock-free структурах (`flume`/`DashMap`/атомики).
- [ ] Идемпотентность задач по `task_id`.
- [ ] Воркер включает лёгкий heartbeat + авто-исключение «сгоревших» на master.
- [ ] Мастер + воркер = единый бинарник, роли через конфиг.
- [ ] Helm/`docker-compose`-шаблон для запуска 1 master + N workers.
