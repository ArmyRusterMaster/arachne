# Правила для нейросетей (AI-агентов) при работе с кодовой базой Arachne

> Этот файл — обязательные правила для LLM-агентов и разработчиков. Цель — единообразный, безопасный и идиоматичный Rust во всём проекте.

## 1. Приоритеты архитектуры

1. **Сначала — максимально общий вариант.** Базовый путь: Fast HTTP (default — `reqwest`+`rustls`, TLS-имперсонация — `wreq` за feature `impersonation` в `arachne-net`) + **собственный** JS/DOM-движок (свои крейты, без готовых браузеров — [11-browser-engines.md](docs/11-browser-engines.md)) + Smart Router. Не привноси тяжёлые зависимости (LLM, eBPF, распределённые ноды, резидентные прокси) в базовый код — они за фича-флагами и в отдельных крейтах (см. [08-development.md](docs/08-development.md), этап 6).
2. **Модульность.** Компоненты — отдельные крейты рабочего пространства (workspace). Не создавай циклических зависимостей между крейтами. Замена движка/транспорта должна затрагивать только один адаптер ([11-browser-engines.md](docs/11-browser-engines.md)).
3. **Typestate-переходы.** Не имитируй состояния сессии флагами `bool`/`enum` в полях — используй Typestate-дженерики ([05-rust-patterns.md](docs/05-rust-patterns.md#53-паттерн-typestate)).
4. **Фазовая дисциплина.** Дорожная карта — три фазы: **A «Штамп-ядро»** (Fast HTTP, парсинг, экспорт, CLI) → **B single-node** (собственный движок, Smart Router) → **C мультинода** ([08-development.md](docs/08-development.md)). Не тащи компоненты будущих фаз в текущую: Фаза A не тянет `boa_engine`/Smart Router в базовый код. Каждая фаза — самодостаточная точка выхода с рабочим продуктом; переход к следующей — по спросу, не по календарю.

## 2. Обязательный паттерн Newtype

**Запрещено** передавать «голые» примитивы между модулями. Всегда оборачивать:

| Домен | Newtype | Вместо |
|---|---|---|
| URL | `Url(String)` | `String` |
| Адрес прокси | `ProxyAddr(String)` | `String` |
| Идентификаторы | `SessionId(Uuid)`, `TaskId(U64)`, `PageId(U64)` | `Uuid`/`u64` |
| Время | `Millis(u64)`, `Seconds(f64)` | `u64`/`f64` |
| Память | `RamLimitBytes(usize)` | `usize` |
| HTML-документ | `Html(Bytes)` | `Bytes` |
| Селектор | `Selector(String)` | `String` |

**Правила:**
- Конструирование — через `TryFrom`/конструктор с валидацией; поля новых типов приватны (`pub struct Url(String)`, не `pub struct Url(pub String)`).
- Никогда не использовать `.0` наружу — вместо этого реализовывать `Display`, `AsRef<str>` и узкие геттеры.
- Ошибки конструирования — отдельные варианты в `thiserror`-ошибках, не паники.

## 3. Обязательный паттерн Typestate

- Состояния сессии кодируются дженериком: `Session<Fast>`, `Session<Headless>` (и в будущем `Session<Engine<X>>`).
- **Невалидные переходы не компилируются**: например, `click()` доступен только `Session<Headless>`; перевод cookie между режимами — только через явные методы `escalate()` / `back_to_fast()`.
- Новые состояния (например, «прогрев», «бан») добавляй как новые маркер-типы + реализацию, не как ветки `match` по полю `state`.
- Число состояний не растёт без необходимости: если состояние влияет только на данные, а не на доступные методы — это enum внутри данных, а не Typestate.

### 3.a. Паттерн Builder (Строитель)

Используется для создания **сложных объектов с множеством параметров**. Два варианта — каждый выбирается по нуждам:

- **Consuming (поглощающий):** методы принимают `self` по значению и возвращают новое состояние, инвалидируя предыдущее. Экономит аллокации (строит отфинальное значение без промежуточных `Arc`), хорошо сочетается с Typestate (невалидная последовательность не компилируется).
  ```rust
  pub struct RequestBuilder { method: Method, url: Url }
  impl RequestBuilder {
      pub fn new(url: Url) -> Self { Self { method: Method::GET, url } }
      pub fn method(self, m: Method) -> Self { Self { method: m, ..self } } // consuming
      pub fn build(self) -> NetRequest { NetRequest { method: self.method, url: self.url } }
  }
  ```
- **Non-consuming (непоглощающий):** методы принимают `&mut self`. Позволяет переиспользовать один и тот же билдер для нескольких объектов и мутить его по месту; требует аккуратного Clone для канонических конфигов сценариев.

Правило: если билдер отражает **линейный конвейер** (каждый шаг один раз) — consuming; если конфиг-объект **переиспользуется** и расширяется — non-consuming.

### 3.b. Стек-аллокации: `Cow` (Clone-on-Write) и `SmallVec`/`ArrayVec`

- **`Cow<'a, B>`** — «экономное» владение: пока данные не менять, работаем со ссылкой без копирования; в момент первой мутации происходит ленивое клонирование (переход в `Borrowed → Owned`). Идеально для хранения «до/после нормализации» URL, заголовков, неинициализированных конфиг-полей.
  ```rust
  use std::borrow::Cow;
  fn normalize<'a>(u: &'a str) -> Cow<'a, str> {
      if u.starts_with("http") { Cow::Borrowed(u) } else { Cow::Owned(format!("https://{u}")) }
  }
  ```
- **`SmallVec`/`ArrayVec`** (`smallvec`/`arrayvec`): если коллекция **почти всегда мала** (известный верхний предел, например `< 8`), размещайте элементы **на стеке** вместо кучи, избегая аллокаций `Vec`. Широко используются в hot-path парсинга (`html5ever`, разбор query-параметров) и в узких структурах заголовков.

  Правило: не тащите `SmallVec` повсюду — только там, где это реально hot path и размер известен; в остальном обычный `Vec`.

## 4. Ошибки

- Библиотечные крейты — `thiserror`, конкретные типы ошибок на крейт (`NetError`, `DomError`, `MacroError`).
- Бинарник (`arachne` CLI) — `anyhow` только на границе `main`.
- Никаких `unwrap()`/`expect()` вне тестов и `const`-контекста. В библиотечном коде — `?` и маппинг ошибок.
- Паника недопустима в воркерах: сбой одной сессии не должен ронять процесс. Возвращай `Result`, используй `tokio::task::spawn` с обработкой `JoinError`.

## 5. Асинхронность

- Рантайм — `tokio` (multi-thread, `#[tokio::main]` только в бинарнике).
- Трейты с async-методами — нативные `async fn` в трейтах (Rust ≥ 1.75) или `async_trait` крейт только если нужна dyn-совместимость.
- Все блокирующие вызовы (файловая система, тяжёлые вычисления) — через `tokio::task::spawn_blocking`.
- Отмена — через `tokio::select!`/`CancellationToken`, не через жёсткий `abort()` без сохранения состояния сессии.

### 5.a. CQRS: команды и запросы обязательны

- Взаимодействие между модулями/потоками — только через **команды** (`Command`) и **запросы** (`Query`) единой шины `Bus` ([05-rust-patterns.md](docs/05-rust-patterns.md#58-cqrs-принцип-команды-и-запросы-для-стриминга-и-мультинодности)).
- Команды изменяют состояние и **идемпотентны**; запросы читают без побочных эффектов.
- Результаты возвращаются **стримами** (`futures::Stream`/каналы с backpressure), а не целыми блоками.
- Переход в мультинодный режим = замена транспорта локальной шины на очередь Redis/NATS, **без изменения вызывающего кода** ([18-distributed.md](docs/18-distributed.md#183-cqrs-команды-и-стриминг-закладывается-с-самогоначала)).

### 5.b. Lock-free структуры данных

- Горячие пути — **без блокирующих мьютексов**: каналы `flume`/`crossbeam-channel`, `DashMap`, атомики (`AtomicU64` и пр.). Никаких `Mutex<HashMap>` на hotspots.
- Данные между потоками — `Arc<Bytes>`/`Bytes` (zero-copy), см. [05-rust-patterns.md](docs/05-rust-patterns.md#57-локфри-структуры-данных-и-асинхронная-конвейерная-обработка).

## 6. Работа с внешними зависимостями

- Сетевой стек — двухбэкендный за трейтом `HttpFetch` (`arachne-net`): default — `reqwest`+`rustls`+`webpki-roots` (pure-Rust, собирается без C-тулчейна), TLS-имперсонация — `wreq` (BoringSSL) за feature `impersonation`. Не добавлять третий HTTP-клиент — дублирование стеков.
- Парсинг: `html5ever` + `scraper`. Передача между крейтами — только `bytes::Bytes`, никаких `String::clone()` больших строк ([05-rust-patterns.md](docs/05-rust-patterns.md#54-использование-bytesbytes-для-zero-copy-передачи-данных)).
- Кэш/пулы: `moka`.
- Трассировка: только `tracing` (не `log`), спаны с полями `session_id`, `url`, `step` ([07-observability.md](docs/07-observability.md)).
- Сериализация: `serde`; сценарии — `serde_yaml`/`serde_json`; версии схем — поле `schema_version` в файлах сценариев.
- LLM/ONNX/eBPF/кластер — **под фича-флагами** и в отдельных крейтах; в базовый `Cargo.toml` не включать (cargo feature: `llm`, `ebpf`, `cluster`, `residential-proxy`).

## 7. Платформозависимость

- Код с зависимостью от ОС — за `#[cfg(target_os = "linux")]` / `#[cfg(windows)]` с реализацией для обоих таргетов или понятным фоллбэком.
- Linux-таргет первоклассный (см. [14-linux-target.md](docs/14-linux-target.md)): сборка в CI на каждый PR, musl-статика для контейнеров.
- Пути в ФС — через `std::path::PathBuf`/`camino::Utf8PathBuf`, никаких конкатенаций строк с разделителями.

## 8. Тестирование

- **Тесты пишутся попутно с кодом (TDD-инвариант).** Принято как обязательный процесс: **нет кода без теста** — каждый новый тип/функция/фича сразу сопровождается тестом в том же коммите. Тесты не откладываются «на потом» и не выносятся в отдельный «этап тестирования».
- **Минорные изменения** (правка, багфикс, рефакторинг, добавление опции) — **минорные тесты**: минимум один тест на изменённое поведение/граничный случай. Объём пропорционален масштабу изменения.
- **Крупные фазы** (новый модуль, переход на другую архитектуру, оптимизация hot-path) — после завершения фазы обязательны **профилирование и оптимизация**:
  - прогнать профилировщик (`perf` / `cargo flamegraph`, `profiling`), замерить CPU/alloc/аллокации;
  - замерить бенчмарки (`criterion`), сохранить baseline; цель — не регрессия ключевых метрик;
  - оптимизировать найденные узкие места (аллокации, lock, memcopy) — с обработкой новых тестов и повторным профилированием. О результате запись в `docs/08-development.md` (профили-отчёт).
- Бенчмарки/профиль в CI — только для hot-path крейтов (`arachne-net`, `arachne-parse`; стриминговый крейт появится в Фазе B), см. [13-cicd-docker.md](docs/13-cicd-docker.md#136-бенчмарки-профиль-и-чек-лист-ci).
- Юнит-тесты в каждом крейте; интеграционные — на крейте CLI.
- Стелс-поведение (jitter, задержки) тестировать с детерминированным RNG (внедряемый trait `Rng`), не системным временем.
- Снэпшоты-фикстуры для DOM-парсинга (маленькие HTML-файлы в `tests/fixtures`).
- Не гонять сетевые тесты в CI по умолчанию — за флагом `--ignored` или mock-сервером.

## 9. Стиль кода

- `cargo fmt` + `cargo clippy -- -D warnings` обязательны в CI ([13-cicd-docker.md](docs/13-cicd-docker.md)).
- Именование: крейты `arachne-*`, типы `UpperCamelCase`, константы `SCREAMING_SNAKE`, фича-флаги `kebab-case`.
- Документация: публичные API — с `///` doc-комментариями и примерами `# Examples`.
- Комментарии — на английском; пользовательская документация (`docs/`) — на русском.

## 10. Работа с документацией

- Любое изменение архитектуры — сначала документация в `docs/`, потом код.
- Новая фича получает: раздел в тематическом файле `docs/`, отметку этапа в [08-development.md](docs/08-development.md), при необходимости — правила в [rules.md](rules.md).
- Не дублировать контент между файлами: одна тема — один файл, остальные ссылаются.

## 11. Коммиты и changelog (обязательная автоматизация)

> Changelog **никогда не ведётся вручную**. Он генерируется автоматически из истории Conventional Commits (см. [13-cicd-docker.md](docs/13-cicd-docker.md#135-автогенерация-changelog)). Поэтому **каждый коммит/PR обязан следовать стилю Conventional Commits**.

- Заголовок коммита: `feat(<scope>): ...`, `fix(<scope>): ...`, `docs(<scope>): ...`, `test(...)`, `refactor(...)`, `chore(...)`.
- **Никогда** не пиши «свободные» заголовки без типа (`updated file`, `fix stuff`) — такой коммит попадёт в `Other` и сломает семантику версии.
- Ломающие изменения — `feat!:`, `fix!:`, либо `BREAKING CHANGE:` в теле. Только они повышают MAJOR-версию.
- Финальные сообщения для AI-агентов: после правок docs/README `feat(docs)`/`docs(...)`, после кода — `feat`/`fix` + scope.
- `CHANGELOG.md` правится только через `git-cliff generate`, руками — **нет**.
- Перед мержем PR обязательна автогенерация: `git-cliff -o CHANGELOG.md` и `cargo-semver-checks` (см. [13-cicd-docker.md](docs/13-cicd-docker.md#135-автогенерация-changelog)).
