# 15. Продвинутая proxy-инфраструктура (Отдельный этап)

> Важное: **продвинутая сеть не блокирует базовый вариант.** Базовый функционал (ротация прокси, кросс-платформенный TCP-стек) описан в [06-infrastructure.md](06-infrastructure.md). Здесь — отдельные **поздние** функции этапа 6 ([08-development.md](08-development.md)), подключаются только после стабилизации ядра.

## 15.1. Отказ от дата-центров (Residential IP Provider Wrapper)

Даже идеальный TLS-отпечаток не спасёт, если запрос идёт из подсети **AWS, DigitalOcean или Hetzner** — антиботы блокируют такие IP превентивно (**ASN-блокировка**).

**Решение:** модуль-обёртка, который:
1. работает с API резидентных/мобильных прокси (Bright Data, Oxylabs, Smartproxy);
2. выполняет **IP Reputation** check: быстрые пинги к «тихим» публичным сервисам перед отправкой основного запроса, чтобы отбраковать скомпрометированные адреса.

## 15.2. Амортизация соединений и Session Sharing

Прокси-пул использует уже «прогретые» TCP/TLS-соединения (Keep-Alive через `moka`, см. [05-rust-patterns.md](05-rust-patterns.md#55-пул-сетевых-соединений-через-moka)). Один «горячий» адрес не используется для двух параллельных сессий одновременно — иначе сервер видит аномальную конкуренцию.

## 15.3. Локальный DNS-резолвер (`trust-dns-resolver`)

Стандартный системный DNS-запрос может:
- выдать ОС хоста и её сетевой конфиг;
- затянуть отправку пакета на сотни мс, ломая тайминги (HTTP/2 Fingerprinting смотрит на неё).

**Решение:** встроенный `tokio`-совместимый классификатор доменов через **DNS-over-HTTPS (DoH)** Cloudflare (1.1.1.1) или Google (8.8.8.8) прямо в `trust-dns-resolver`. Плюс:
- ретрансляция долгих DNS-колдунов через `tokio`;
- защита от DNS-отравления: DoH + валидация ответов;
- полный контроль над сетевым стеком от начала до конца (без слежки от системного резолвера ОС).

## 15.4. Управление пулом прокси

- **Health-check**: периодическая проверка доступности и «чистоты» IP;
- **репутация**: ведётся сквозная репутация адреса (кол-во успешных/банов/429) и авто-исключение «сгоревших»;
- **ротация по расписанию**: интервал, цепочки запасных адресов на сессию;
- **прокси-автофейл**: через MUX-интерфейс пула, см. [05-rust-patterns.md](05-rust-patterns.md#52-паттерн-newtype) (типы `ProxyId`, `ProxyPoolHandle`).

## 15.5. Интеграция с Smart Router

Пул не отдельный «терминал», а call context для Smart Router ([03-smart-routing.md](03-smart-routing.md)): выбор адреса напрямую влияет на решение «HTTP или Headless». При длинной цепочке сбоев — роутер автоматически пробует следующего провайдера, увеличивая таймауты по экспоненте.

## 15.6. Чек-лист для реализации (Late-Stage)

- [ ] Поддержка SOCKS5/HTTP прокси-URL-схем с аутентификацией на уровне CRUD пула.
- [ ] Консолидация «сгоревших» IP и репутации.
- [ ] DoH-резолвер в сетевое ядро обоих режимов (`rquest` и собственный движок).
- [ ] Интеграция выбора прокси и профиля сессии в транзакции Router.
- [ ] Тесты: эмуляция «сгоревшего» IP, DoH-режим, ротация юридического канала.

> Если из-за частых банов/таймаутов на целевых сайтах базовый MVP буксует — можно временно развернуть комбайн на домашнем интернете (стационарный роутер) вместо дата-центровых ферм: реальные домашние IP (без «сгоревшего» ASN) дают качественно иные шансы против антиботов. Это быстрая проверка, не требующая покупки резидентных прокси.
