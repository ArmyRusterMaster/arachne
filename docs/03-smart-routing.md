# 3. Автоматический выбор режима (Smart Routing)

> **Приоритет высокий.** Это сердце комбайна: система сама решает, когда использовать сверхбыстрый **Fast HTTP** режим, а когда переключиться в **Headless-браузерный** режим. Реализуется в общем варианте, поэтому заслуживает отдельного внимания на ранних этапах.

## 3.1. Два режима

| Режим | Движок | Когда | Стоимость |
|-------|--------|-------|-----------|
| **Fast HTTP** | `rquest` | Статический HTML, API, без JS-защит | Дешёвый, быстрый |
| **Headless** | собственный движок (JS `boa_engine` + DOM `html5ever`) | JS-валидации, динамический контент, действия пользователя | Дорогой, медленный |

## 3.2. Логика принятия решения

Не запускать тяжёлый JS/DOM-движок для каждого сайта — это неэкономно. Конвейер принимает решение в два уровня.

### Уровень 1. Эвристики перед первым запросом (стеометки URL)
До первого запроса оценить целевой URL:
- известные JS-тяжёлые сайты (SPA, React) — сразу режим Headless;
- чистый API/JSON-endpoint — сразу Fast HTTP;
- неизвестный — начинать с Fast HTTP.

### Уровень 2. Эскалация по ответу сервера (runtime)
1. Сначала делается «дешёвый» запрос через `rquest` (Fast HTTP).
2. Если сервер возвращает:
   - код **403 / 429**;
   - JS-заглушку (Cloudflare Challenge Page, DataDome, Akamai challenge);
   - пустое тело при ожидаемом контенте,
   → система автоматически «эскалирует» задачу: поднимает **ту же сессию** (перенося cookie) в собственном JS/DOM-движке для прохождения валидации.
3. После прохождения в разумное время л видим быстрый контент → задача может **снова вернуться** в Fast HTTP режим.

## 3.3. Схема

```
[ Сценарий / Макрос ]
        |
        v
[ Smart Router ] ── эвристики по URL ────────────────┐
        |                                            |
        | (первый запрос)                            v
        v                                      [ Fast HTTP / rquest ]
[ Fast HTTP / rquest ] ──────────► ответ ок ──► [ ДАННЫЕ ]
        |
        | 403 / 429 / JS-challenge
        v
[ Headless / собственный движок (boa+dom) ]
   (несём ту же сессию + cookie)
        |
        | прошёл валидацию
        v
[ ДАННЫЕ ]  ◄── (опция) возврат в Fast HTTP
```

## 3.4. Требования к реализации (MVP)

- [ ] Единый `StealthSession`, умеющий «переезжать» между режимами с сохранением cookie/LocalStorage.
- [ ] Детектор ответа: распознавание challenge-страниц (по заголовкам `cf-chl-*`, `Set-Cookie` с защитными метками, маркерам HTML).
- [ ] Параметр `mode: auto | fast | headless` в конфигурации сессии.
- [ ] Лимит попыток эскалации (не бесконечные переключения).
- [ ] Метрики: сколько запросов ушло по Fast vs Headless, пороги троттлинга.
