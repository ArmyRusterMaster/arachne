# 19. SaaS-платформа: low-code конструктор, мультитенантность, биллинг, API

> **Статус:** перспективное направление, отложено на **поздний этап** (после стабилизации базового ядра, см. [08-development.md](08-development.md) этап 6). Не блокирует базовый функционал — подключается отдельным слоем/крейтами за фича-флагом `saas`.

Цель — превратить Arachne из CLI-«комбайна» в **SaaS low-code платформу**: пользователь **собирает сценарий парсинга из блоков** (drag-and-drop) без знания кода, платит по подписке или за запрос, а платформа **бесшовно** скрывает за собой резидентные прокси, ротацию, стелс и распределение нагрузки.

## 19.1. Целевой пользовательский сценарий (бесшовность)

1. Пользователь открывает веб-UI, видит **конструктор блоков** (палитра слева, канвас по центру).
2. Перетаскивает блоки: `HTTP GET`, `CLICK`, `FILL` (форма), `EXTRACT`, `LOOP`, `IF/CONDITION`, `PAGINATE`, `CAPTCHA-HANDLER`.
3. Соединяет блоки линиями — получается **сценарий** (сохраняется как JSON/YAML-схема — тот же формат, что в интерпретаторе макросов `arachne-macro`).
4. Нажимает «Запуск» — платформа **самостоятельно** выбирает Fast HTTP или собственный JS/DOM-движок, подбирает чистый резидентный прокси и профиль фингерпринта; пользователь ничего об этом не знает.
5. Результат — таблица/JSON/стрим. Оплата списывается **за количество запросов** (или по подписке).

> Главные принципы: **максимальная простота и прозрачность для пользователя**; вся сложность (прокси, стелс, эскалация) — скрыта платформой.

## 19.2. Мультитенантность

- **Изоляция тенантов** на уровне данных: каждому тенанту (`tenant_id`) — свой namespace в БД, своя конфигурация прокси/лимитов. Идентификаторы сессий/задач (`SessionId`, `TaskId`) содержат `tenant_id`.
- **Изоляция рантайма:** контексты воркеров разделяются по тенантам (`DashMap<TenantId, Pool>`); один упавший воркер не роняет соседний тенант (ч.5 «Ошибки» в [rules.md](../rules.md)).
- **Ресурсные квоты** тенанта: лимит параллельных сессий, RAM, кол-во запросов/мес — через **Token Bucket** на входе API (паттерн из [04-architecture.md](04-architecture.md#44-защита-от-oom-out-of-memory-на-базе-token-bucket)).
- **Идентичность прокси:** пулы резидентных прокси одного тенанта не «перемешиваются» с другими (изоляция IP-репутации).

## 19.3. Авторизация и аутентификация

- Модель пользователей и ролей («Владелец», «Редактор», «Только запуск»), RBAC на уровне блоков/тенанта.
- Сессии пользователей — JWT/`X-Session-ID` в веб-слое; внутренние сессии `arachne` (`StealthSession`) не смешиваются с учётными.
- Для разработчиков — внешняя авторизация по **API-ключам** (раздел 19.5a).

## 19.4. Привязка биллинга: подписки и оплата за запрос
- **Тарифы на подписке:** размер пула прокси, кол-во параллельных сессий, объём данных.
- **Pay-as-you-go:** оплата за **количество обработанных запросов/страниц** (usage-based billing). Счётчик списаний ведётся на уровне `TaskId` (атомики `AtomicU64` / учётные счётчики).
- Оплата через биллинг-провайдер (Stripe и аналоги); вебхуки на событие оплаты, автоматическое снятие лимитов при просрочке.
- **Квоты и предупреждения:** при приближении к лимиту — уведомления; после исчерпания — блокировка запуска с понятным сообщением (HTTP `429`).

## 19.5. Резидентные прокси как сервис (скрытно и бесшовно)

- Платформа **сама поставляет** резидентные/мобильные прокси (см. [15-proxy-infra.md](15-proxy-infra.md)); пользователь их не настраивает — только выбирает «страну/качество».
- Пулы прокси **скрыты от пользователя** (он не видит IP), но логируются для диагностики → трассировка ([07-observability.md](07-observability.md)) на уровне спанов `session_id`, `proxy_pool`.
- Ротация и мониторинг репутации IP на стороне платформы: автоматическая замена при бане — без участия пользователя.

## 19.5a. Публичный API для разработчиков (интеграция по ключам)

- **REST API** (`axum`): запуск сценариев, получение статусов, стрим результатов, управление прокси.
- **API-ключи:** `Authorization: Bearer ara_sa_...`; скоуп на роли/тарифе тенанта; ревокация и ротация.
- **SDK/клиенты** на Rust и др.; **OpenAPI**-спецификация (JSON-schema) публикуется как артефакт.
- **Webhooks** на события `task.completed`, `task.failed`, `quota.exhausted`.

## 19.5b. Веб-слой: `axum` + `leptos` (гибрид SSR + CSR)

- **Бэкенд:** `axum` (асинхронный веб-фреймворк) — REST-роуты для API, авторизация, биллинг, метрики. Вписывается в существующий `tokio`-стек проекта.
- **Фронтенд:** `leptos` — Rust-фреймворк с гибридной моделью:
  - **SSR** (Server-Side Rendering): быстрый первый рендер HTML на сервере, SEO;
  - **CSR/hydration** (Client-Side Rendering): интерактивная часть, drag-and-drop канвас конструктора блоков.
- Одна кодовая база на Rust: типы сценариев, ошибки переиспользуются между ядром и веб-слоем (крейт `arachne-web`).
- `leptos` собирается в WASM для клиента, SSR отдаётся на `axum`-роутах.
## 19.6. Архитектура SaaS-слоя (крейты)

```
arachne-saas/
├── arachne-api/        # axum: REST API, маршруты, валидация (openapi)
├── arachne-ui/         # leptos: SSR-страницы + WASM-клиент (конструктор)
├── arachne-billing/    # тарифы, квота, счётчики, вебхуки оплат
├── arachne-multi/      # tenancy: изоляция, RBAC, ключи
├── arachne-runner/     # оркестрация: приём задачи -> пул воркеров arachne
└── shared/             # домен-типы (Newtype), схемы сценариев, DTO
```

Каждый крейт — отдельный; серверный слой вызывает ядро `arachne` через **CQRS-шину** (команда `RunScenario(ScenarioId)` / запрос `GetTaskStatus`), поэтому переход в кластер ([18-distributed.md](18-distributed.md)) прозрачен.

## 19.7. Безопасность и скрытость для конечного пользователя

- Пользователь не видит IP прокси, фингерпринты, TLS-отпечатки — всё под капотом.
- Данные тенантов не смешиваются: шифрование at rest и в транзите (TLS), секреты/ключи — в хранилище секретов.
- Следование [07-security.md](07-security.md) и [rules.md](../rules.md): новые зависимости не раздувают базовое ядро краулера.

## Roadmap внедрения

1. Стабильный CLI `arachne` (`src/`) и стабильное API сценариев.
2. Слой `arachne-runner` + `arachne-multi` (tenancy, ключи).
3. Фронт `axum` + `leptos`: минимальный просмотр задач и статуса.
4. Конструктор из блоков: граф блоков (drag-and-drop) → валидный JSON-сценарий.
5. Биллинг: подписки + pay-per-request, квоты, оплата.
6. Публичный API + webhooks для сторонних разработчиков.

---

> Правило: базовый краулер работает **без** SaaS-слоя. SaaS-слой подключается как отдельный фронтенд+бэкенд, который дёргает ядро по CQRS-шине — ядро не зависит от него.
