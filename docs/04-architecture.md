# 4. Базовая архитектура

> Здесь описан **максимально общий вариант** — то, что реализуется в первую очередь. Продвинутые подсистемы (распределённые ноды, eBPF, LLM) вынесены в отдельные файлы и подключаются на поздних этапах.

> **Статус (Фаза A):** реализованы фундаментальные пункты — транспорт с ротацией прокси/ретраями/джиттером (`arachne-net`), CQRS-каркас (`arachne-cqrs`), zero-copy `Html(Bytes)` на границе крейтов (§4.5 частично — `Bytes` вместо строк, стриминг узлов — Фаза B). Остальное (§4.1 Headless, §4.2 cookie-мост, §4.4 token bucket, §4.6 прогрев) — Фаза B.

## 4.1. Двухрежимная архитектура (Hybrid Core)

Ядро комбайна — единая сессия, работающая в двух режимах (подробный разбор выбора режима — [03-smart-routing.md](03-smart-routing.md)):
- **Fast HTTP** (`reqwest`/`wreq`) — для парсинга API и статического HTML;
- **Headless** (собственный движок: `boa_engine` JS + `html5ever` DOM) — для эмуляции действий пользователя. Готовый браузер **не внедряем** ([11-browser-engines.md](11-browser-engines.md)).

## 4.2. Синхронизация сессий (Cookie-Jar Sharing)

Единое сквозное хранилище **Cookie и LocalStorage**. Авторизация, пройденная в HTTP-клиенте, мгновенно доступна в собственном JS/DOM-движке, и наоборот. Это критично для Smart Router: при эскалации сессия «переезжает» без потери состояния.

## 4.3. Изолированная многопоточность

Каждый JS-контекст `boa_engine` запускается в **чистом изолированном пуле памяти**, что предотвращает утечки ресурсов при долгой работе. Коммуникация между контекстами и воркерами — через **lock-free структуры данных** (каналы `flume`/`crossbeam`, `DashMap`), чтобы избежать блокировок и конкурентных пауз (см. [05-rust-patterns.md](05-rust-patterns.md#57-локфри-структуры-данных-и-асинхронная-конвейерная-обработка)).

## 4.4. Защита от OOM (Out Of Memory) на базе Token Bucket

Тяжёлые сайты с утечками памяти (memory leaks) могут «уронить» бинарник. В рантайм `tokio` добавляется планировщик с ограничением на **максимальный объём выделяемой RAM для каждого контекста страницы**:
- если страница превышает лимит в **40 МБ** — жёсткий перезапуск контекста **с сохранением cookie**.

## 4.5. Прогрессивный стриминг DOM (Zero-Copy DOM Streaming)

Вместо передачи всего HTML-текста из DOM-парсера в `scraper` — **zero-copy передача ссылок на узлы (nodes) памяти** (крейт `bytes`), чтобы экономить CPU и RAM на гигантских страницах (например, бесконечные ленты соцсетей). Поток данных идёт по lock-free каналам, не копируясь между потоками.

## 4.6. Пул прогретых сессий (Session Pre-warming)

Заблаговременный запуск сессий в фоновом режиме, которые **нагуливают «траст»**:
- прогревают cookie;
- заходят на нейтральные трастовые сайты (Google, Wikipedia),
прежде чем перейти к парсингу сложного целевого ресурса.

## 4.7. Потоковая (стриминговая) модель обработки

Вся обработка — **конвейерная и асинхронная**: каждый узел (получение HTTP → DOM → данные → результат) — отдельный actor-подобный поток, соединённый lock-free каналами с backpressure. Это:
- держит загрузку CPU/RAM на пике эффективности;
- **естественно масштабируется в мультинодный режим**: тот же конвейер переносится на кластер без переписывания ([18-distributed.md](18-distributed.md));
- основано на CQRS-принципе: **команды**, изменяющие состояние, и **запросы**, читающие данные, разделены.

## 4.8. Архитектурный чек-лист (базовый вариант)

- [ ] Единый `StealthSession` для обоих режимов.
- [ ] Единое cookies/LocalStorage-хранилище между режимами.
- [ ] Токен-бакет на память (лимит 40 МБ на контекст) с перезапуском контекста.
- [ ] Zero-copy передача DOM (`bytes::Bytes`).
- [ ] Пул прогретых сессий.
- [ ] Собственный модульный движок — без готовых браузеров ([11-browser-engines.md](11-browser-engines.md)).
- [ ] Потоковая модель на lock-free структурах + CQRS-разделение команд/запросов ([18-distributed.md](18-distributed.md#184-локфри-структуры-данных)).
